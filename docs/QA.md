# Питання по коду: ймовірні запитання і відповіді

Згруповано за темами. Кожна відповідь короткa — так, щоб її можна було сказати вголос.

## ООП

**— Навіщо тут взагалі класи? React же функціональний.**

React відповідає за інтерфейс, а не за бізнес-логіку. Правила «ціна не може бути
відʼємною», «на електронну книгу знижка 15%», «з «Нового» замовлення не можна
одразу в «Виконано»» — це логіка домену. Якщо розкидати її по компонентах, вона
дублюється і губиться. У класах вона в одному місці, і компоненти просто її викликають.

**— Що дає `new.target === Entity`?**

Це захист абстрактного класу. `Entity` і `Product` самі по собі — не товари,
створювати їх напряму немає сенсу. Якщо хтось напише `new Entity()`, отримає
зрозумілу помилку одразу, а не дивну поведінку десь пізніше.

**— Покажіть приклад поліморфізму.**

`getDiscountPercent()`: у `Product` повертає 0, у `EBook` — 15, у `AudioBook` — 10.
Кошик рахує суму так:

```js
items.reduce((sum, item) => sum + item.book.getFinalPrice() * item.quantity, 0)
```

Кошик не знає типу книги. Додамо завтра клас `Collection` зі знижкою 25% —
кошик міняти не доведеться.

**— Навіщо приватні поля `#price`, якщо можна просто `this.price`?**

Щоб не можна було записати некоректне значення в обхід перевірки.
`book.price = -50` кине `RangeError`, бо йде через сеттер. Якби поле було
публічним, будь-який компонент міг би зіпсувати дані.

**— Що таке `BookFactory` і навіщо вона?**

З сервера приходить JSON: `{ format: 'ebook', … }`. Треба перетворити це на
обʼєкт потрібного класу. Фабрика тримає реєстр `format → клас`:

```js
static registry = { paper: PaperBook, ebook: EBook, audio: AudioBook };
```

Додати новий формат = один рядок у реєстрі. Без фабрики довелося б писати
`if/else` у кожному місці, де створюється книга.

**— Чому `CartItem` не успадковує `Entity`?**

Бо це не сутність, а value-object: у нього немає власного життєвого циклу
та ідентифікатора в базі. Він існує лише як пара «книга + кількість».

**— Скільки всього класів у проєкті?**

26: 13 моделей (`core/models`), 9 валідаторів (`core/validation`),
4 адаптери сховищ (`core/storage`), плюс ієрархія репозиторіїв (`core/api`).

## React, хуки, пропси

**— Які хуки використані?**

Вбудовані: `useState`, `useEffect`, `useMemo`, `useCallback`, `useRef`,
`useContext`, `useId`. З React Redux: `useSelector`, `useDispatch`.
З React Router: `useNavigate`, `useParams`, `useLocation`, `useSearchParams`.
Плюс 5 власних: `useForm`, `useCart`, `useDebounce`, `usePersistentState`, `useMediaQuery`.

**— Навіщо `useDebounce`?**

Пошук фільтрує 24 книги — це швидко. Але на кожній натиснутій літері летить
`dispatch`, перераховуються селектори і перемальовується сітка. На каталозі
з тисячами товарів це помітно гальмувало б. Debounce чекає 300 мс паузи в наборі
і лише тоді оновлює Redux.

**— Де тут `useMemo` і навіщо?**

Наприклад, у `HomePage`: підбірки «Бестселери» і «Новинки» — це сортування
всього каталогу. Без `useMemo` воно виконувалось би на кожен рендер,
навіть коли змінилась тема або лічильник кошика.

**— Чому `BookCard` обгорнутий у `memo`?**

На сторінці каталогу 8 карток. Коли міняється стан кошика, перемальовується
сторінка. `memo` порівнює пропси і не перемальовує ті картки, чия книга не змінилась.

**— Що таке PropTypes і навіщо вони, якщо це не TypeScript?**

Це перевірка типів пропсів у режимі розробки. Якщо передати число замість рядка
або забути обовʼязковий проп, у консолі зʼявиться попередження. У `BookCard`
навіть перевіряється клас: `PropTypes.instanceOf(Book)` — тобто в картку не можна
випадково передати «сирий» JSON замість обʼєкта моделі.

**— Чому `useForm` повертає `fieldProps(name)`?**

Щоб не повторювати в JSX п'ять однакових пропсів для кожного поля.
Замість `value={} onChange={} onBlur={} name={} error={}` пишемо `{...form.fieldProps('email')}`.

**— Що робить `useCart`?**

Це фасад. Компонент викликає `add(book)`, а не
`dispatch(addToCart({ bookId: book.id, quantity: 1 }))`. Крім того, всередині
вже є перевірка наявності та показ тоста. Якщо замінити Redux на щось інше,
зміниться лише цей файл, а не всі компоненти.

## Redux і Context

**— Чому і Redux, і Context? Це ж дублювання.**

Ні, у них різні задачі. Redux — для даних, які часто змінюються і потребують
похідних обчислень: каталог, фільтри, кошик. Там потрібні мемоізовані селектори,
async thunks і DevTools. Context — для значень, що змінюються рідко: тема,
поточний користувач, черга сповіщень. Заводити для теми окремий слайс —
надлишково.

**— Чому не покласти все в Context?**

Context перемальовує **всіх** споживачів при будь-якій зміні значення.
Якби кошик жив у Context, кожне натискання «+» перемальовувало б увесь каталог.
`useSelector` підписує компонент лише на потрібний шматок стану.

**— Чому в сторі лежить `{ bookId, quantity }`, а не сама книга?**

Два аргументи. По-перше, Redux вимагає серіалізовний стан — обʼєкти класів туди
класти не можна. По-друге, якби ми скопіювали книгу в кошик, а адмін змінив
ціну — у кошику лишилась би стара. Зберігаємо тільки id, а решту беремо з каталогу.

**— Тоді як компоненти отримують обʼєкти класів?**

Через селектори:

```js
export const selectCartModels = createSelector(
  [selectBookModels, selectCartItems],
  (books, cart) => cart.map(({ bookId, quantity }) => {
    const book = books.find((b) => b.id === bookId);
    return book ? new CartItem(book, quantity) : null;
  }).filter(Boolean)
);
```

`createSelector` кешує результат — обʼєкти перестворюються лише коли
змінився каталог або кошик.

**— Що таке `persistMiddleware` і навіщо він?**

Це власний middleware Redux. Після кожної дії з префіксом `cart/` або `filters/`
він записує відповідний шматок стану в localStorage. Альтернатива — писати
`localStorage.setItem` у кожному редюсері (це побічний ефект, у редюсерах так не можна)
або в кожному компоненті (дублювання). Middleware робить це в одному місці.

**— Що робить `.unwrap()` у `dispatch(createBook(...)).unwrap()`?**

Async thunk ніколи не кидає помилку назовні — він повертає екшен `rejected`.
`.unwrap()` перетворює відхилений результат назад у виняток, щоб можна було
написати звичайний `try/catch` або дочекатись успіху перед закриттям модалки.

## Валідація

**— Чому валідація винесена в класи, а не написана прямо у формі?**

Щоб правила можна було переиспользовувати і комбінувати. `EmailValidator`
використовується і в логіні, і в реєстрації, і в оформленні замовлення.
Опис форми стає декларативним:

```js
phone: [new RequiredValidator('Вкажіть телефон'), new PhoneValidator()]
```

**— Що таке шаблонний метод у `Validator`?**

Базовий клас реалізує `validate()` — загальний алгоритм: викликати `check()`
і, якщо `false`, повернути повідомлення. Наслідники пишуть тільки `check()`.
Так логіка «як повідомити про помилку» не дублюється у дев'яти класах.

**— Чому `PhoneValidator` успадковує `PatternValidator`, а не `Validator`?**

Бо перевірка телефону — це та сама перевірка за регуляркою, плюс попереднє
очищення від пробілів і дужок. Тому він перевизначає `check()`, чистить рядок
і викликає `super.check(cleaned)`.

**— Коли показуються помилки?**

Після `blur` (коли користувач пішов з поля) або після спроби відправити форму.
Показувати помилку під час набору — поганий UX: людина ще друкує email,
а їй вже кажуть, що він невірний. При відправці всі поля позначаються як
«тронуті», і фокус переводиться на перше невалідне поле.

## Дані та збереження

**— Три способи збереження — навіщо стільки?**

- **cookie** — сесія і тема. Cookie мають термін життя й автоматично
  відправляються на сервер; для авторизації це природний механізм.
- **localStorage** — кошик, фільтри, історія переглядів. Обʼєм більший,
  і ці дані не потрібні серверу при кожному запиті.
- **json-server (БД)** — книги, замовлення, користувачі. Це спільні дані.

**— Що станеться, якщо не запустити json-server?**

Нічого страшного. `BaseRepository` спробує запит, впіймає помилку, поставить
`useApi = false` і далі працюватиме з копією даних у localStorage. Саме тому
зібраний проєкт можна викласти на статичний хостинг, і він буде повністю робочим.

**— Пароль зберігається у відкритому вигляді?**

Ні, у вигляді хешу — але це **навчальний** хеш (проста згортка рядка в число),
і я це чітко позначив у коментарі. У реальному проєкті хешування паролів —
задача бекенду (bcrypt або argon2), клієнт паролі взагалі не хешує.
Тут це зроблено, щоб продемонструвати інкапсуляцію: поле `#passwordHash`
приватне і назовні через `toJSON()` не потрапляє.

**— Чому в `toJSON()` користувача немає пароля?**

Свідомо. Це приклад того, що інкапсуляція — не лише про сеттери:
модель сама вирішує, які дані віддавати назовні.

## Маршрутизація і доступ

**— Як захищена адмін-панель?**

Компонентом-обгорткою `RequireAuth adminOnly`. Він дивиться на контекст
авторизації: якщо користувач не залогінений — редірект на `/login`
із запамʼятовуванням, куди він хотів потрапити; якщо залогінений, але не
адмін — редірект на головну.

**— Це справжній захист?**

Ні, і це важливо розуміти. Клієнтський захист — це UX: не показувати
користувачу те, чим він не може скористатись. Справжня перевірка прав
завжди на сервері. Тут json-server навчальний і прав не перевіряє.

**— Що таке `permissions` у класі `User`?**

Гетер, який наслідники розширюють:

```js
// Customer
get permissions() { return [...super.permissions, 'cart:write', 'order:create']; }
// AdminUser
get permissions() { return [...super.permissions, 'catalog:write', 'admin:panel']; }
```

Це рольова модель. Замість перевірок «якщо роль === admin» по всьому коду
пишемо `user.can('catalog:write')` — і легко додати третю роль (наприклад, модератора).

## Стилі, ергономіка, продуктивність

**— Чому CSS Modules, а не Tailwind чи styled-components?**

CSS Modules дають ізоляцію класів (немає конфліктів імен) без додаткових
залежностей і без рантайм-навантаження. Стилі лишаються звичайним CSS —
їх легко читати й пояснювати.

**— Як зроблена темна тема?**

Усі кольори — CSS-змінні у `:root`. Темна тема перевизначає ті самі змінні
під селектором `[data-theme='dark']`. `ThemeProvider` виставляє атрибут
на `<html>` і зберігає вибір у cookie на рік. Початкове значення —
з cookie, а якщо його немає — із системної теми через `prefers-color-scheme`.

**— Що зроблено для доступності?**

`:focus-visible` для клавіатурної навігації, `aria-invalid` і `aria-describedby`
на полях із помилками, `role="alert"` на тексті помилки, `aria-live` на тостах,
закриття модалки по Esc із поверненням фокусу, підписи `aria-label` на іконкових
кнопках, посилання «Перейти до вмісту» на початку сторінки,
підтримка `prefers-reduced-motion`.

**— Як таблиця адмінки поводиться на телефоні?**

Через CSS перетворюється на картки: `thead` ховається, кожен рядок стає блоком,
а заголовок колонки підставляється з атрибута `data-label` через `::before`.
Ніякого JavaScript.

**— Чому обкладинки книг намальовані, а не картинки?**

Свідоме рішення: зовнішні картинки — це биті посилання, повільне завантаження
і залежність від інтернету. `BookCover` генерує градієнт детермінованою
хеш-функцією від назви книги: та сама книга завжди має ту саму обкладинку.

## Що можна покращити (корисно сказати самому)

- **Тести.** Логіка в `core/` не залежить від React, тому вкривається
  юніт-тестами (Vitest) без рендеру. Це найочевидніший наступний крок.
- **Реальний бекенд** замість json-server і JWT замість навчального хешу.
- **RTK Query** замість ручних thunks — дав би кешування й інвалідацію з коробки.
- **Віртуалізація списку** (react-window), якщо каталог виросте до тисяч позицій.
- **Код-спліттінг** сторінок через `React.lazy` — зараз бандл 326 КБ (110 КБ gzip),
  адмінку можна не вантажити звичайним покупцям.
