# Доповідь: план виступу (10–12 хвилин)

Нижче — сценарій захисту: що показувати на екрані і що казати.
Час указано орієнтовно.

---

## Слайд 1. Що це за проєкт (1 хв)

> «Це інтернет-магазин книг на React. Каталог із 24 книг трьох форматів —
> паперові, електронні та аудіокниги. Є пошук із фільтрами, кошик,
> оформлення замовлення, авторизація з ролями та адмін-панель.»

**Стек:** Vite + React 18 · Redux Toolkit · React Router · CSS Modules · json-server

**Показати:** головну сторінку.

---

## Слайд 2. Демонстрація для покупця (2,5 хв)

Живий прохід по сценарію — не слайди, а сам застосунок:

1. **Каталог** → показати фільтри: набрати «Орвелл» у пошуку
   (звернути увагу: список оновлюється не миттєво, а через 300 мс — це debounce)
2. Поставити галочку «Аудіокнига» → лишились 4 книги
3. Посунути повзунок ціни, змінити сортування на «Ціна: спочатку дешевші»
4. **Сторінка книги** → показати, що характеристики різні у різних форматів:
   в аудіокниги — диктор і тривалість, в електронної — формат файлу та розмір,
   у паперової — обкладинка й вага
5. **Додати в кошик** → зʼявився тост, лічильник у шапці виріс
6. **Кошик** → змінити кількість, ввести промокод `BOOK10`
7. **Оформлення** → натиснути «Підтвердити» з порожніми полями,
   показати помилки валідації; ввести телефон у неправильному форматі
8. Заповнити коректно → замовлення створено, редірект на «Мої замовлення»
9. **Перезавантажити сторінку** → кошик і тема на місці (localStorage + cookie)

## Слайд 3. Демонстрація адмінки (1,5 хв)

1. Вийти, зайти як `admin@book.ua / admin123`
2. У шапці зʼявився пункт «Адмінка» — у покупця його немає
3. **Статистика** — виторг, кількість замовлень, середній чек
4. **Книги** — додати нову книгу (показати, що поля форми змінюються
   залежно від обраного формату), відредагувати, видалити
5. **Замовлення** — змінити статус щойно створеного замовлення.
   Звернути увагу: у списку доступні лише дозволені переходи
   (з «Новий» не можна одразу в «Виконано»)

## Слайд 4. Архітектура (2 хв)

Показати схему з `docs/ARCHITECTURE.md`:

```
pages / components     ← React
hooks / context / store ← стан
core/api               ← дані
core/models + validation + storage  ← чистий JS, без React
```

> «Головна ідея: у папці `core` немає жодного імпорту React. Це звичайний
> JavaScript — бізнес-логіку можна протестувати без рендеру або перенести
> в інший проєкт.»

## Слайд 5. ООП: ієрархія класів (2 хв)

Відкрити `src/core/models/` і показати дерево:

```
Entity → Product → Book → PaperBook / EBook / AudioBook
Entity → User → Customer / AdminUser
Entity → Order
```

Три речі, які варто показати в коді:

**1. Інкапсуляція** — `Product.js`:
```js
#price;
set price(value) {
  if (Number.isNaN(+value) || +value < 0) throw new RangeError('Ціна не може бути відʼємною');
  this.#price = Math.round(value * 100) / 100;
}
```
> «Ціна — приватне поле. Зіпсувати її ззовні неможливо.»

**2. Поліморфізм** — `EBook.js`:
```js
getDiscountPercent() { return 15; }   // у Product було 0
```
> «Кошик рахує суму, викликаючи `getFinalPrice()`. Він не знає і не має знати,
> яка саме книга перед ним.»

**3. Бізнес-правило всередині моделі** — `Order.js`:
```js
static TRANSITIONS = { new: ['processing', 'cancelled'], … };
setStatus(next) {
  if (!this.canTransitionTo(next)) throw new Error('Неможливо змінити статус…');
}
```
> «Правила переходу статусів живуть у моделі. Адмін-панель їх не дублює —
> вона просто питає в моделі, що дозволено.»

## Слайд 6. Redux і Context: чому обидва (1,5 хв)

| | Redux Toolkit | Context API |
|---|---|---|
| Каталог, фільтри, кошик, замовлення | ✅ | |
| Тема, користувач, сповіщення | | ✅ |

> «Redux там, де дані часто змінюються і потрібні мемоізовані обчислення.
> Context — там, де значення змінюється рідко, і заводити цілий слайс
> було б надлишково.»

Показати `store/selectors.js`:

```js
export const selectBookModels = createSelector(
  [selectRawBooks],
  (raw) => BookFactory.createMany(raw)
);
```

> «У Redux за правилами лежать прості обʼєкти. А компонентам потрібні обʼєкти
> класів із методами. Місток між ними — цей мемоізований селектор:
> фабрика запускається тільки коли каталог реально змінився.»

## Слайд 7. Валідація форм (1 хв)

Показати `core/validation/`:

```
Validator → PatternValidator → EmailValidator
                             → PhoneValidator
```

```js
export const checkoutSchema = new ValidationSchema({
  phone: [new RequiredValidator('Вкажіть телефон'), new PhoneValidator()],
});
```

> «Хук `useForm` не містить жодного правила. Правила приходять ззовні як схема.
> Тому одна й та сама логіка форми обслуговує і оформлення замовлення,
> і логін, і форму книги в адмінці.»

## Слайд 8. Збереження даних — три механізми (1 хв)

| Механізм | Що зберігає | Чому саме він |
|----------|-------------|---------------|
| **cookie** | сесія, тема | живе 7/365 днів, автоматично йде на сервер |
| **localStorage** | кошик, фільтри, історія переглядів | великий обсяг, не засмічує кожен запит |
| **БД (json-server)** | книги, замовлення, користувачі | спільні дані для всіх користувачів |

Показати `core/storage/` — ієрархію адаптерів:

> «Усі три сховища за одним інтерфейсом. Якщо браузер заблокував localStorage,
> підставляється MemoryStorageAdapter, і решта коду цього не помічає.»

## Слайд 9. Підсумок і плани (0,5 хв)

**Що зроблено:** 60+ файлів, 26 класів, 4 слайси Redux, 3 контексти, 5 власних хуків,
9 сторінок, адаптив від 320px, темна тема, деплой на Vercel.

**Що можна розвинути:**
- реальний бекенд (ASP.NET Core / Node) замість json-server
- JWT замість учбового хешу пароля
- юніт-тести для `core/` (Vitest) — логіка вже ізольована від React
- оптимістичні оновлення та кешування (RTK Query)
